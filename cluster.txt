## Step 16 – Configure Constraints (Group-Level, ENSA2)
 
Both stacks are resource groups, so the cross-stack constraints are set

**once, at the group level** — `RES_SAP_ATQ` ↔ `RES_ERS_ATQ`. Nothing needs

to be set for the members *inside* each group; that's handled automatically

by group membership (Step 15).
 
### Ordering — ASCS ↔ ERS relationship
 
Not a startup-order gate — its real purpose is: *if the ASCS group ever

lands on the same node as the ERS group, ERS should relocate so it can

re-sync the lock table elsewhere.*

```

pcs constraint order start RES_SAP_ATQ then stop RES_ERS_ATQ kind=Optional symmetrical=false

```

- `kind=Optional` — advisory, only applied if both actions happen to occur together

- `symmetrical=false` — stopping/restarting `RES_SAP_ATQ` will **not** force `RES_ERS_ATQ` to stop
 
### Colocation — ASCS ↔ ERS anti-affinity
 
Soft negative score (not `-INFINITY`, which is an ENSA1-only rule) — lets

the ASCS group fail over onto the ERS group's node in a 2-node cluster when

node01 is down, while still steering the cluster to keep them apart when a

choice exists:

```

pcs constraint colocation add RES_ERS_ATQ with RES_SAP_ATQ -5000

```
 
### Location Preferences
 
Prefer the ASCS group on u0bvsapatq001:

```

pcs constraint location RES_SAP_ATQ prefers u0bvsapatq001=100

```
 
Prefer the ERS group on u0bvsapatq002:

```

pcs constraint location RES_ERS_ATQ prefers u0bvsapatq002=100

```
 
These are preferences, not hard restrictions. If one node fails, Pacemaker

can still relocate resources if needed.
 
> **Removed from this revision:** the earlier draft included
> `pcs constraint location RES_SAP_ATQ rule score=2000 RES_ERS_ATQ eq 1`.
> This traces back to a real, documented Red Hat pattern — RHEL for SAP
> Solutions' "Configuring HA clusters to manage SAP NetWeaver or SAP
> S/4HANA Application server instances" guide gives the example
> `pcs constraint location s4h_ascs20 rule score=2000 runs_ers_S4H eq 1`,
> used to force the ASCS instance to follow the node where ERS is running
> after a failover. Two things make it wrong for this build:
> 1. **Architecture mismatch** — Red Hat scopes this rule explicitly to
>    **ENSA1**: "it must be ensured that the (A)SCS instance moves to the
>    node where the ERS instance is running when failover is happening."
>    This environment is **ENSA2**, where ASCS does not need to follow ERS;
>    the anti-affinity colocation (`-5000`) and the Optional/non-symmetrical
>    order constraint already in this runbook are the ENSA2-appropriate
>    equivalents for the same coordination problem.
> 2. **Attribute mismatch** — even under ENSA1, the rule checks a
>    purpose-built **node attribute** (`runs_ers_S4H` in Red Hat's example)
>    that the ERS resource agent sets automatically when ERS is running on
>    a node — not a resource or group name. The draft substituted the
>    resource group name `RES_ERS_ATQ` in its place, but nothing in this
>    cluster sets a node attribute by that name (confirmed via
>    `crm_mon -A -1`, which shows no Node Attributes section at all), so the
>    rule would never evaluate true even if it were architecturally
>    applicable here.
>
> Net: correctly scoped to ENSA1 use cases only, and would need a real
> node-attribute mechanism (not a group-name substitution) to function even
> there. Dropped from this ENSA2 build.
 
### (Optional, recommended) Split-brain protection
 
For a 2-node ENSA2 cluster, consider enabling `priority-fencing-delay` so

the node currently running ASCS wins any fencing race during a split-brain

event:

```

pcs property set priority-fencing-delay=15s

```

Confirm the exact recommended value and prerequisites (SBD/fencing agent

support, `pcmk_delay_max`, and — for a true 2-node cluster —

`two_node`/`no-quorum-policy` settings) with your OS vendor's current

documentation before enabling, and validate the fencing race behavior in a

test failover first.
